Artifact and rationale. I originally created the CS-300 Advising Assistance Program for my Data Structures, Algorithms, and Design coursework. It is a C++ console application that loads course information from a CSV file, stores courses in a hash table, displays the course list in alphanumeric order, and lets a user search for a course and view its prerequisites. I continued with this artifact because I could run and test it locally.

Changes made. I improved input validation and error handling throughout the program. It validates menu input before converting it to a number, handles invalid and out-of-range choices, checks for empty file names, reports file-opening failures clearly, detects files with no valid course records, and gives clearer feedback when a requested course does not exist or an empty course ID is entered. I also used const references where appropriate and added comments to improve maintainability.

Skills and outcomes. This work demonstrates practical software engineering, debugging, testing, and computing practices. It improved the reliability, maintainability, and usability of the application while preserving its original data-structure functionality.

Reflection. The enhancement reinforced the importance of testing beyond the normal successful path. I tested valid and invalid file names, successful course loading, invalid course searches, empty course IDs, invalid menu selections, and normal lookups. Getting the older project running in a current local environment was a challenge, but rebuilding and testing it step by step helped me work through those issues instead of assuming the code would work unchanged.

Read the enhancement narrative

Artifact and rationale. The CS-300 Advising Assistance Program loads course information from a CSV file, stores records in a hash table, sorts courses for display, and allows users to search for courses and view prerequisites. It demonstrates how data structures and algorithms can solve a practical problem.

Changes made. I added a sorted vector and binary search so the program can compare two approaches to course lookup. I also added a search comparison feature and a performance test with 100,000 search operations. The program reports average O(1) for hash-table lookup, O(log n) for binary search, and O(n log n) for sorting.

Testing and trade-offs. Both methods found CSCI200. The test used eight courses and measured 10,723 microseconds for hash-table search and 26,299 microseconds for binary search. This helped me see that theoretical complexity and measured runtime are related but not identical. Binary search requires sorted data, while the hash table provided faster lookup in this particular test.

Reflection. I learned to evaluate the requirements and trade-offs of an algorithm instead of choosing one based only on Big-O notation. Keeping the original hash-table search and adding binary search separately allowed me to compare both methods while preserving the existing program. The enhanced program built successfully and completed the test.
